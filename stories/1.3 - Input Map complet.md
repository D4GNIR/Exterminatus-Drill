# 1.3 - Input Map complet

## Phase

Phase 1 — Fondations techniques du projet Godot

## Statut

Terminée

## Objectif

Déclarer dans `project.godot` les **12 actions** du tableau « Contrôles » du CDC, avec leurs touches par défaut, afin qu'aucun script du projet n'ait jamais besoin de tester une touche en dur.

## Dépendances

- `1.1 - Initialisation du projet Godot 4`

## Critères d'acceptation

1. La section `[input]` de `project.godot` définit exactement ces 12 actions, avec ces noms littéraux :
   `move_up`, `move_down`, `move_left`, `move_right`, `drill`, `brake`, `use_item_1`, `use_item_2`, `use_item_3`, `toggle_inventory`, `toggle_journal`, `pause`.
2. Les touches par défaut correspondent au CDC :
   | Action | Touches |
   |---|---|
   | `move_up` | Z, Flèche haut |
   | `move_down` | S, Flèche bas |
   | `move_left` | Q, Flèche gauche |
   | `move_right` | D, Flèche droite |
   | `drill` | Espace |
   | `brake` | Shift |
   | `use_item_1` / `use_item_2` / `use_item_3` | 1 / 2 / 3 |
   | `toggle_inventory` | I, Tab |
   | `toggle_journal` | J |
   | `pause` | Échap |
3. Chaque action déclare un `deadzone` explicite et une liste `events` syntaxiquement valide (`InputEventKey` au format Godot 4).
4. Aucune action supplémentaire hors CDC n'est déclarée ; aucune action du CDC n'est manquante.
5. Le choix `keycode` vs `physical_keycode` est **explicite et justifié** en Notes (voir point à trancher ci-dessous), et appliqué de façon homogène à toutes les actions.
6. Aucun script existant ne teste une touche en dur (`event.keycode == KEY_...`) — vérifiable par `grep` sur `KEY_` dans `scripts/`.
7. **[H]** *Project Settings > Input Map* affiche les 12 actions avec les bonnes touches (`TM-1.4`).
8. **[H]** Chaque touche déclenche bien son action, une seule fois par appui (`TM-1.5`).

## Référence cahier des charges

- « Contrôles » — tableau complet des actions, Input Map et touches par défaut.
- « Règles autorisées » / « Règles interdites ou limitées » — les règles associées aux actions (pas de forage vers le haut, annulation des directions opposées) sont **hors périmètre de cette story** : elles sont implémentées en phases 2 et 3. Ici, seule la déclaration des actions est en jeu.

## Notes / décisions

**Arbitrage utilisateur — tranché le 2026-08-29.** **Q2 — Mapping clavier : `physical_keycode`.** Toutes les touches directionnelles sont déclarées par leur **position physique** (W/A/S/D), ce qui donne ZQSD sur AZERTY et WASD sur QWERTY sans code conditionnel. Les flèches restent en secours sur chaque action.
  - Conséquence à ne pas oublier : un libellé de touche affiché à l'écran ne doit **jamais** être écrit en dur (« Appuyez sur Z »), puisqu'il dépend de la disposition du joueur. Utiliser `OS.get_keycode_string(DisplayServer.keyboard_get_keycode_from_physical(...))` le jour où un écran d'aide affichera les touches. Point à contrôler à l'audit.
  - S'applique aussi aux touches non directionnelles (`drill`, `brake`, `use_item_1..3`, `toggle_inventory`, `toggle_journal`, `pause`) par cohérence.
- Le remappage complet est explicitement **post-MVP** (« Backlog après MVP » du CDC) : ne pas construire d'écran d'options ici.
- Une éventuelle scène de test d'input (affichage des actions pressées) est autorisée pour faciliter `TM-1.5`, mais doit être placée dans `scenes/` avec un nom explicite et rattachée à cette story dans les artefacts, sinon l'audit la relèvera comme fichier orphelin (point A5).

**Décisions prises pendant la story (2026-08-30).**

- **Périmètre tenu au strict minimum** : la story n'ajoute que la section `[input]` de `project.godot`. Aucun `.gd`, `.tscn` ni `.tres` n'a été créé ; `[autoload]` (stories `1.4`/`1.5`) et `run/main_scene` (story `1.6`) n'ont pas été touchés.
- **Scène de test d'input non créée** (bien qu'autorisée par la story) : avant `1.6`, la phase ne produit aucune scène, et un `.tscn` de debug non rattaché à une fonctionnalité serait un candidat au point d'audit A5 (fichier orphelin / résidu de test). La vérification a été faite autrement, par relecture de l'`InputMap` réellement chargé par le moteur (voir ci-dessous), ce qui est une preuve plus forte que l'affichage à l'écran pour tout ce qui n'est pas ergonomie. Le critère `[H]` `TM-1.5` (chaque touche déclenche son action, une seule fois par appui) reste donc à valider à la main en `1.8`. **Point à arbitrer par le `po`** : `qa/plan-tests-manuels.md:48` prévoit pour `TM-1.5` de « lancer la scène de test d'input (ou lire l'Output) », or aucune scène ni aucun script n'existera avant `1.6`. Deux supports possibles sans créer d'artefact ici : utiliser le mode d'écoute de touche de *Project Settings > Input Map* (qui affiche la touche captée), ou reporter l'exécution de `TM-1.5` après `1.6`, la scène `Main` pouvant porter un affichage de debug des actions pressées.
- **Codes de touches vérifiés auprès du moteur** avant écriture (script jetable hors dépôt) plutôt que recopiés de mémoire : `KEY_W=87`, `KEY_A=65`, `KEY_S=83`, `KEY_D=68`, `KEY_UP=4194320`, `KEY_DOWN=4194322`, `KEY_LEFT=4194319`, `KEY_RIGHT=4194321`, `KEY_SPACE=32`, `KEY_SHIFT=4194325`, `KEY_1..3=49..51`, `KEY_I=73`, `KEY_TAB=4194306`, `KEY_J=74`, `KEY_ESCAPE=4194305`.
- **Format de sérialisation `InputEventKey` obtenu du moteur** et non inventé : un projet jetable créé dans le scratchpad a servi à faire écrire à `ProjectSettings.save()` la forme canonique de Godot 4.7.2, recopiée ensuite à l'identique. Conséquence assumée : `"device":16`, qui est la valeur par défaut d'un `InputEventKey` neuf en 4.7 (et non `-1`, valeur de `DEVICE_ID_EMULATION` des versions antérieures). Le champ `device` n'intervient pas dans la correspondance touche → action pour un événement clavier ; la correspondance a été vérifiée explicitement (voir preuves).
- **Correspondance CDC → position physique** : le CDC décrit un clavier AZERTY (`Z`, `Q`). En `physical_keycode`, la position de `Z` AZERTY est `KEY_W` et celle de `Q` AZERTY est `KEY_A`. Le fichier déclare donc W/A/S/D, qui produisent `ZQSD` sur AZERTY et `WASD` sur QWERTY — conforme au CDC pour le joueur français, jouable pour un joueur QWERTY.
- **`deadzone` explicite à 0.2** sur les 12 actions (valeur par défaut du moteur, rendue visible dans le fichier). Sans effet sur des événements clavier, mais exigé par le critère 3 et nécessaire le jour où une action recevra un axe de manette.
- **Un commentaire d'en-tête** a été ajouté juste avant `[input]` pour que la règle « pas de libellé de touche en dur » soit lisible dans le fichier lui-même, et pas seulement dans cette story.

**Règle opposable pour les phases ≥ 4 (UI).** Puisque toutes les touches sont déclarées par position physique, **aucun libellé de touche ne doit être écrit en dur** dans une scène, un texte d'aide ou un tutoriel (« Appuyez sur Z » est faux sur QWERTY). L'affichage doit être dérivé à l'exécution, par exemple :
`OS.get_keycode_string(DisplayServer.keyboard_get_keycode_from_physical(event.physical_keycode))` à partir du premier `InputEventKey` de `InputMap.action_get_events(<action>)`.

**Conflits connus avec les actions `ui_*` intégrées** (non traités ici, à arbitrer en phase 4) : `drill` (Espace) recouvre `ui_accept`, `pause` (Échap) recouvre `ui_cancel`, `toggle_inventory` (Tab) recouvre `ui_focus_next`, et les flèches recouvrent `ui_up/down/left/right`. C'est sans effet tant qu'aucune UI focusable n'existe ; le point sera traité par la discipline de lecture d'input du point d'audit F4 (`_unhandled_input` côté gameplay, entrées consommées par l'UI).

**Preuves de vérification (Godot 4.7.2 stable, headless, exécutées depuis la racine).**

1. `godot --headless --path . --script <scratchpad>/check_input.gd` — relit `InputMap` tel que chargé par le moteur : **12 actions non-`ui_`**, exactement celles du CDC, aucune en trop, aucune manquante ; **17 événements**, tous `InputEventKey`, tous avec `keycode = 0` et `physical_keycode ≠ 0` ; **17 touches physiques distinctes** pour 17 événements, donc **aucun doublon** entre actions ; `deadzone = 0.20` partout. `InputMap.event_is_action()` renvoie vrai pour les 12 touches principales et pour les 5 touches secondaires (4 flèches + Tab).
2. `godot --headless --import` puis `godot --headless --editor --quit` : **aucune ligne `ERROR:` / `SCRIPT ERROR:`**, code retour 0, et `project.godot` inchangé après coup (md5 identique avant/après) — les commentaires rédigés à la main survivent.
3. `grep -rn "KEY_\|keycode\|scancode" scripts/` : **aucune occurrence** (le dossier ne contient encore aucun script) — critère 6 satisfait à ce stade, à re-contrôler à chaque sprint.
4. Le refus `Can't run project: no main scene defined` de `godot --headless --quit` reste attendu jusqu'à la story `1.6` : `run/main_scene` n'a délibérément pas été ajouté ici.
