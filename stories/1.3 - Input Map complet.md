# 1.3 - Input Map complet

## Phase

Phase 1 — Fondations techniques du projet Godot

## Statut

À faire

## Objectif

Déclarer dans `project.godot` les **12 actions** du tableau « Contrôles » du CDC, avec leurs touches par défaut, afin qu'aucun script du projet n'ait jamais besoin de tester une touche en dur.

## Dépendances

- `1.1 - Initialisation du projet Godot 4`

## Critères d'acceptation

1. La section `[input]` de `project.godot` définit exactement ces 12 actions, avec ces noms littéraux :
   `move_up`, `move_down`, `move_left`, `move_right`, `drill`, `brake`, `use_item_1`, `use_item_2`, `use_item_3`, `toggle_inventory`, `toggle_journal`, `pause`.
2. Les touches par défaut correspondent au CDC :
   | Action | Touches |
   |---|---|
   | `move_up` | Z, Flèche haut |
   | `move_down` | S, Flèche bas |
   | `move_left` | Q, Flèche gauche |
   | `move_right` | D, Flèche droite |
   | `drill` | Espace |
   | `brake` | Shift |
   | `use_item_1` / `use_item_2` / `use_item_3` | 1 / 2 / 3 |
   | `toggle_inventory` | I, Tab |
   | `toggle_journal` | J |
   | `pause` | Échap |
3. Chaque action déclare un `deadzone` explicite et une liste `events` syntaxiquement valide (`InputEventKey` au format Godot 4).
4. Aucune action supplémentaire hors CDC n'est déclarée ; aucune action du CDC n'est manquante.
5. Le choix `keycode` vs `physical_keycode` est **explicite et justifié** en Notes (voir point à trancher ci-dessous), et appliqué de façon homogène à toutes les actions.
6. Aucun script existant ne teste une touche en dur (`event.keycode == KEY_...`) — vérifiable par `grep` sur `KEY_` dans `scripts/`.
7. **[H]** *Project Settings > Input Map* affiche les 12 actions avec les bonnes touches (`TM-1.4`).
8. **[H]** Chaque touche déclenche bien son action, une seule fois par appui (`TM-1.5`).

## Référence cahier des charges

- « Contrôles » — tableau complet des actions, Input Map et touches par défaut.
- « Règles autorisées » / « Règles interdites ou limitées » — les règles associées aux actions (pas de forage vers le haut, annulation des directions opposées) sont **hors périmètre de cette story** : elles sont implémentées en phases 2 et 3. Ici, seule la déclaration des actions est en jeu.

## Notes / décisions

**Arbitrage utilisateur — tranché le 2026-08-29.** **Q2 — Mapping clavier : `physical_keycode`.** Toutes les touches directionnelles sont déclarées par leur **position physique** (W/A/S/D), ce qui donne ZQSD sur AZERTY et WASD sur QWERTY sans code conditionnel. Les flèches restent en secours sur chaque action.
  - Conséquence à ne pas oublier : un libellé de touche affiché à l'écran ne doit **jamais** être écrit en dur (« Appuyez sur Z »), puisqu'il dépend de la disposition du joueur. Utiliser `OS.get_keycode_string(DisplayServer.keyboard_get_keycode_from_physical(...))` le jour où un écran d'aide affichera les touches. Point à contrôler à l'audit.
  - S'applique aussi aux touches non directionnelles (`drill`, `brake`, `use_item_1..3`, `toggle_inventory`, `toggle_journal`, `pause`) par cohérence.
- Le remappage complet est explicitement **post-MVP** (« Backlog après MVP » du CDC) : ne pas construire d'écran d'options ici.
- Une éventuelle scène de test d'input (affichage des actions pressées) est autorisée pour faciliter `TM-1.5`, mais doit être placée dans `scenes/` avec un nom explicite et rattachée à cette story dans les artefacts, sinon l'audit la relèvera comme fichier orphelin (point A5).
